Review remediation proceeds through evidence-gated commits

Eight agents move tests, fixes, and stack history through review-gated phases.

whetstone-envs · 2026-07-24

What must be true before implementation begins?

operating contract
  • One worktree per agent. Every prompt uses a literal worktree path and states that all task paths are relative to that directory.
  • No overlapping parallel edits. Scoring, pool, manifest, and probes may run together; the two instance findings run under one sequential owner.
  • The primary checkout stays untouched during each agent wave. Integration happens only after a findings-first review and focused verification.
  • One committer owns the target branch. Agents edit temporary branches without committing; the primary agent reviews, commits in the worktree, then cherry-picks the reviewed commit.

How will test quality be established?

phases 1–2

Phase 1Independent audit

One high-reasoning read-only agent audits every current test for fragility, stale expectations, weak assertions, misleading names, and missing contract coverage.

Deliverable: ranked findings with exact files, concrete failure modes, and proposed deterministic tests.

Phase 2Agreed test implementation

A different implementation agent receives only the accepted audit items. It owns tests/core/ and may adjust shared fixtures there.

Gate: tests must fail for the intended pre-fix reason, not for incidental implementation details.

CheckpointRefresh PR review comments

After the test commit, refetch every current inline comment and review on PR 1. Reproduce relevant reports, merge them with the local findings, remove duplicates, and publish one remediation ledger before any source fix begins.

This checkpoint may expand or narrow the five implementation owners, but it does not permit fixes before the test phase is reviewed and committed.

How will the remaining stack be rebased safely?

phase 4

Audit firstMap the Graphite stack

  1. Record branch parents, local/remote tips, ownership, dirty state, and commits unique to each branch.
  2. Identify semantic conflicts caused by the hard API cutovers, especially split and aggregation callers.
  3. Write a branch-by-branch rebase order and validation matrix before mutating history.

Execution gateRestack, verify, submit

Refresh local main, restack one branch at a time, resolve conflicts against the reviewed contracts, run focused checks per branch and the full suite at the tip, then execute gt submit --stack.

No push to main; pull-request bases remain the fork’s main branch.
